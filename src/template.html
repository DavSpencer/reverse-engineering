CONCEPT What RE Actually Is
The Core Idea

When a developer writes an Android app, they write it in Java or Kotlin. That source code gets compiled — transformed into machine instructions the device can execute. You never get that source code when you download an app from the Play Store. What you get is the compiled output.

Reverse engineering is the process of working backwards from that compiled output to understand what the code does — and then modifying it. You don't need the original source. The compiled output contains everything the app needs to run, which means it contains everything you need to read and change it.

Why Android Specifically Is Reversible

Android apps compile to a bytecode format called DEX (Dalvik Executable). Unlike native machine code (x86, ARM assembly), bytecode sits one level above raw hardware instructions. It's designed to run on a virtual machine — the Android Runtime — not directly on the CPU. This design choice, made for portability and security sandboxing, is exactly what makes RE possible at a practical level.

DEX bytecode preserves class structure, method names (unless obfuscated), field names, and type information from the original source. A tool like JADX can reconstruct something very close to the original Java from it. Even with obfuscation, the logic is always intact — only the names change.

// COMPARE TO NATIVENative code compiled to ARM or x86 assembly loses almost all semantic information. Class names, method names, types — gone. Reversing a .so file requires Ghidra or IDA and weeks of manual analysis. DEX bytecode gives you back most of that for free. That's why apps that need serious protection move their DRM to native .so files.

javac / kotlinc — Source to .class

The Java or Kotlin compiler transforms source files into .class files — standard JVM bytecode. One .class file per class. At this stage the code targets the Java Virtual Machine, not Android specifically.

These .class files still don't run on Android — they need one more step.

d8 — .class to DEX

d8 (previously dx) is Google's DEX compiler. It takes all the .class files and merges them into one or more classes.dex files — Dalvik bytecode that Android can actually run.

Key things d8 does during this conversion:

  • Merges all classes from all .class files into a single DEX class pool
  • Converts JVM stack-based instructions to Dalvik's register-based instructions
  • Deduplicates string constants across the entire app into a shared string pool
  • Applies R8 (built-in optimizer + ProGuard replacement) if enabled — this is where obfuscation happens
  • Splits into multiple DEX files if the method count exceeds 65,536 (the multidex limit)
Multidex — Why There Are Multiple DEX Files

DEX files use a 16-bit index for method references. That caps you at 65,536 unique method references per DEX file. Large apps hit this limit easily — one app + all its third-party libraries can have 200,000+ methods.

Solution: split into multiple DEX files. classes.dex is the primary. classes2.dex, classes3.dex etc. are overflow files. Android loads all of them at startup.

// FOR PATCHINGThe class you need to patch might be in classes2.dex or classes3.dex, not the primary. In MT Manager's APK editor, you can tap into any DEX file separately. JADX loads all DEX files automatically when you open the APK.
baksmali / smali — DEX to Smali and Back

baksmali is a disassembler — it converts DEX bytecode into Smali, a human-readable text representation of the Dalvik instructions. MT Manager runs baksmali internally when you open a DEX file in the Smali editor.

smali is the assembler — it does the reverse, converting Smali text back to DEX bytecode. MT Manager runs smali internally when you save your edits.

You never run these tools manually. MT Manager handles both sides. But understanding that this conversion is happening explains why saving a method immediately validates your bytecode — the smali assembler is running and catching errors.

JADX — DEX Back to Java

JADX goes further than baksmali — instead of producing Smali assembly, it decompiles DEX back to Java pseudocode. It reconstructs if/else, for loops, try/catch, class hierarchies, generics.

The output is not real source code — it's a reconstruction, and it's not always perfect. Complex control flow, lambda expressions, and heavy obfuscation can confuse it. But even imperfect Java pseudocode is dramatically faster to read than raw Smali.

The workflow: use JADX to understand the logic and find where to patch, then use MT Manager to make the actual edit in Smali. JADX is your map. MT Manager is your scalpel.

RUNTIME Dalvik vs ART
What Actually Runs Your Code

Android has had two runtimes. Understanding both helps you understand what's happening when an app runs — and why certain patches work the way they do.

Dalvik — The Original (Android 1.0 – 4.4)

Dalvik was Android's original virtual machine. It interprets DEX bytecode at runtime using JIT (Just-In-Time) compilation — translating frequently-run bytecode to native machine code on the fly, caching the result.

Key characteristic: register-based VM. Unlike the JVM which is stack-based, Dalvik explicitly names registers (v0, v1, p0…) in every instruction. This is why Smali looks so different from JVM bytecode — it directly reflects Dalvik's register architecture. Dalvik is gone in modern Android, but the bytecode format it defined (DEX) is still what all Android apps compile to today.

ART — Android Runtime (Android 5.0+, current)

ART replaced Dalvik in Android 5.0 Lollipop. The key difference: ART uses AOT (Ahead-Of-Time) compilation. When you install an app, ART compiles the DEX bytecode to native machine code right then. The native code is stored in /data/dalvik-cache/ as an OAT file.

Modern ART uses a hybrid approach: some AOT compilation at install, JIT compilation for code paths discovered at runtime, and profile-guided optimization that improves over time as the app is used.

// WHY THIS MATTERS FOR REART still ships with and runs from DEX files — the OAT cache is just an optimization. When you patch the DEX in an APK and reinstall, ART recompiles your patched DEX fresh. The patch runs. The OAT cache is rebuilt from your modified DEX automatically.
FORMAT The APK — What It Really Is
An APK Is Just a ZIP

An APK (Android Package) is a standard ZIP file with a .apk extension. Every piece of data the app needs to run is inside it. Rename any APK to .zip on your PC and it opens in any archive tool.

In MT Manager: long-press any APK → Open As Archive — you're browsing the ZIP. You can extract individual files, edit them, and re-add them. That's all "modding" is at the file level.

Binary XML — AndroidManifest.xml

The AndroidManifest.xml inside an APK is NOT standard text XML. It's been compiled to a compact binary format called AXML (Android Binary XML) by aapt2 during the build. Opening it in a text editor shows garbage.

MT Manager automatically detects and decodes binary XML when you tap it in the APK editor — you see human-readable XML. When you save it, MT Manager re-encodes to binary. This is why you can edit the manifest in MT Manager but not in a plain text editor on the raw APK.

The same binary format applies to all XML files in res/. APKTool also handles this decoding/re-encoding, which is why it's the preferred tool for resource-heavy mods.

DEX How DEX Bytecode Works
DEX File Structure

A DEX file is a carefully structured binary file. Understanding its layout helps you understand why decompilers work so well — the format preserves a lot of the original source structure.

SECTIONCONTENTS
HeaderMagic bytes (dex\n035\0), checksum, SHA-1 hash, file size, section offsets. The magic bytes confirm it's a valid DEX file.
String poolEvery string literal in the entire app — class names, method names, field names, string constants — deduplicated into one indexed list. This is why string searching is so fast and so powerful for RE.
Type poolAll type descriptors (class names in Smali format) referenced in the file. References into the string pool.

// THE STRING POOL IS YOUR FRIENDBecause every string in the entire app is deduplicated into one searchable pool, when you search for a string in MT Manager's DEX editor or JADX, you're searching one indexed list. That's why string search is fast and reliable even in large apps — and why it's almost always your first move.
Register-Based vs Stack-Based VM

Understanding this difference makes Smali make sense immediately.

JVM (stack-based): instructions push and pop values from a stack. To add two numbers: push first number, push second number, execute ADD (which pops both and pushes the result). Instructions don't name operands — they just operate on whatever's on top of the stack.

Dalvik (register-based): instructions name their operands explicitly using register identifiers. To add two numbers: add-int v0, v1, v2 — v0 gets the result, v1 and v2 are the inputs. Every instruction says exactly where it reads from and writes to.

Register-based bytecode is more verbose — each instruction is longer — but it's also easier to read and reason about. When you look at a Smali method, you can trace data flow directly: const/4 v0, 0x1 puts 1 in v0, return v0 returns it. No stack state to track.

SMALI The Language You Edit
What Smali Is

Smali is a text representation of Dalvik bytecode — it maps 1-to-1 with the binary DEX instructions. Every Smali instruction corresponds to exactly one DEX opcode. There's no ambiguity, no abstraction, no compiler optimization between them. What you write in Smali is exactly what runs.

The name comes from the Icelandic word for "assembly". It was created by Ben Gruver (JesusFreke) as a companion to baksmali (the disassembler). Together they are the canonical tools for reading and writing Dalvik bytecode — and they're built into MT Manager.

Smali vs Java — The Same Thing, Different View
// Java (what the dev wrote):
public boolean isPremium() {
    return true;
}

// Smali (what you edit in MT Manager):
.method public isPremium()Z
    .registers 2
    const/4 v0, 0x1
    return v0
.end method

Same logic. One is source, one is bytecode assembly. The Smali version has explicit register allocation (.registers 2), explicit type encoding (Z for boolean), and explicit register use (v0 holds the value). Everything implicit in Java is explicit in Smali.

Why You Edit Smali and Not Java

JADX produces Java pseudocode for reading — it's a decompiler output, not real source. You cannot compile it back. The reconstruction is imperfect and JADX doesn't produce code the smali assembler can work with directly.

Smali is the actual bytecode representation. MT Manager's Smali editor writes directly to DEX — no compilation step, no translation. Edit a method, save it, the DEX is updated. Direct, lossless, reversible. That's why Smali is the editing layer, even though Java is easier to read.

// THE WORKFLOWRead logic in JADX (Java view). Understand what to change. Find the same method in MT Manager (Smali view). Make the change in Smali. The two tools complement each other perfectly.
ADB Android Debug Bridge
What ADB Is

ADB (Android Debug Bridge) is a command-line tool that lets you communicate with an Android device from your PC. It's part of Android Platform Tools — a free download from Google, no full Android Studio needed.

For RE, ADB is used for: pulling APKs off the device, reading crash logs (logcat), running shell commands, pushing files, launching activities manually, and connecting Frida server. Not required for on-device patching with MT Manager alone, but essential for the full workflow.

  5. Verify. Run adb devices again. You should see your device listed as device (not unauthorized).

ANALYSIS Static vs Dynamic
Two Modes of RE — Know Which to Use

Static analysis means examining the app without running it. You read DEX, Smali, and decompiled Java. You trace code paths with your eyes. You patch the APK file directly. This is what MT Manager + JADX give you. Fast to set up, no root required, works on any device.

Dynamic analysis means examining the app while it runs. You hook methods, intercept calls, read memory, observe real behavior at runtime. This is what Frida + Objection give you. Requires root. Slower to set up, but can crack things static analysis can't touch.

PROTECTIONS What You'll Face
The Protection Landscape

Apps use layered protections. Knowing what each one is tells you what tool to reach for and roughly how hard the job is.

Level 1 — No Protection

Many apps — especially indie and small studio apps — ship with no obfuscation, no integrity checks, no root detection. Class names are clear (PurchaseManager), methods are readable (isPremium()). JADX shows clean Java. One or two methods to patch, sign, done. These are the starting point for learning.

Level 2 — ProGuard / R8 Obfuscation

The default for any app built with Android's release pipeline. R8 (the modern ProGuard replacement) renames classes, methods, and fields to short meaningless names: a, b, c. The logic is 100% intact. Only names change.

Broken by: string search (strings are never obfuscated), billing SDK anchors (third-party classes are never renamed), JADX rename + call graph tracing, logcat log tags.

Level 3 — String Encryption

DexGuard, Allatori, and custom obfuscators encrypt string literals. Instead of "is_premium" in the code, you see a call to a decrypt helper: a.a(1337). String search finds nothing useful.

Broken by: hook the decrypt method with Frida, log every decrypted string at runtime. Or: reverse the decryption algorithm statically (usually XOR or AES with a hardcoded key in the same class) and decrypt all constants yourself with a Python script.

Level 4 — APK Integrity Checks

The app reads its own APK signature at runtime and compares it to a hardcoded expected value. If you modify the APK and resign with your keystore, the signatures don't match — app detects tampering and closes or disables features.

// What the check looks like in JADX:
PackageInfo info = pm.getPackageInfo(pkg, GET_SIGNATURES);
String sig = Base64.encode(info.signatures[0].toByteArray());
if (!sig.equals(EXPECTED_SIG)) { kill(); }

Broken by: find this check (search for getSignatures, GET_SIGNATURES, signatures[0]) and patch it to always pass. Or hook getPackageInfo() with Frida to return a fake signature matching the expected value.

Level 5 — Root Detection

App checks if the device is rooted and refuses to run or disables features if it is. Common checks: does /system/bin/su exist? Is the Superuser app installed? Does which su return a path? Is the build tag test-keys?

Broken by: Magisk with MagiskHide (now Shamiko) hides root from specific apps. Or: hook the root detection methods with Frida/Objection (android root disable). Or: find and patch the root check methods statically.

Level 6 — SSL Certificate Pinning

App hardcodes the expected TLS certificate (or its hash) for its API server. When you try to intercept HTTPS traffic with mitmproxy or HTTP Toolkit, the app sees a certificate from your proxy instead of the expected one and refuses to connect — or crashes.

Broken by: Objection one-liner: android sslpinning disable. Or: patch the pinning validation method to always return valid. Or: use network security config in the manifest to allow user-added CAs (works for some apps, not apps that implement pinning in code).

Level 7 — Native DRM / .so Files

The most serious protection. License validation, integrity checks, and subscription state are moved entirely into a native .so library compiled from C/C++/Rust. The DEX code just calls into the native library and receives a yes/no. All the logic is in ARM assembly — no class names, no method names, no types.

Broken by: Ghidra or IDA Pro for static analysis (weeks of work on complex apps). Frida for hooking the JNI bridge call between Java and the native library. Emulation-based analysis. This is advanced territory — most subscription gates don't go this far.

Level 8 — Dynamic Class Loading

The APK contains almost no code. On first run, it downloads an encrypted DEX from a server, decrypts it locally, and loads it with DexClassLoader. The actual logic never exists on disk in readable form. Static analysis of the APK finds a shell.

Broken by: Frida hooks on DexClassLoader to intercept the path of the loaded DEX file. Pull that file from /data/data/com.app/files/ or similar. Open it in JADX like a normal APK.

WORKFLOW The Complete Pipeline
  1. SETUP — Install MT Manager VIP. Create your signing keystore (≡ → Keystore Management → Create). Set it as default. Set up ADB if you'll be doing advanced work.
  2. EXTRACT — Get the target APK. MT Manager → Functions → Installed Apps → Extract APK. Copy to a working folder. Never work on the original.
  3. READ — Open the APK in JADX on PC. Browse the package structure. Find where billing logic lives. Note class names and method signatures. Understand the gating logic.
  4. ASSESS PROTECTIONS — Is it obfuscated? Does JADX show a.b.c or real names? Does it do network license checks? Does it check its own signature? This determines your approach.
  5. HUNT — Find the exact method to patch. Use string search, billing SDK anchors, logcat, Frida tracing — whichever fits the protection level. See the HUNT tab for all 9 methods.
  6. DECODE — If obfuscated, map the scrambled names to real purposes using type inference, JADX rename, log tags, and cross-references until you've identified the gate method.
  7. PATCH — Open the DEX in MT Manager. Navigate to the method. Tap Edit. Write your Smali patch (always-return-true, flip branch, early return, etc.). Update .registers. Save.
  8. SHIP — Save the APK in MT Manager (floppy disk). Sign it with your keystore. Uninstall original (different signature = required). Install your mod.
  9. TEST — Launch the app. Trigger the previously locked feature. Does it open? If yes — done. If the app crashes or the feature is still locked, go to step 10.
  10. DEBUG — Run adb logcat AndroidRuntime:E *:S. Read the crash. Find the method named in the stack trace. Fix the register count or restore what you broke. Repeat from step 7.

KEYSTORE Your Signing Identity
What a Keystore Is

A keystore is a file that contains a cryptographic key pair — a private key and a self-signed certificate. When you sign an APK with it, Android records the certificate fingerprint. On every future install or update of that APK, Android checks that the new APK is signed by the same certificate.

This is why you can't just install your modded APK over the Play Store version — different certificates. You must uninstall first. But once you've installed your mod, future updates you sign with the same keystore install cleanly as updates without uninstalling.

Create Your Keystore — Step by Step
  1. MT Manager → tap ≡ (top right hamburger) → Keystore Management.
  2. Tap + (or New) → Create Keystore.
  3. Keystore path: tap the folder icon → navigate to /sdcard/Mods/ → type filename my.jks → confirm. This is where the keystore file saves.
  4. Keystore password: any password you'll remember. Use the same as key password to keep it simple.
  5. Key alias: a label for this key entry. "mykey" or "patch" or anything. Not security-critical.
  6. Key password: same as keystore password is fine.
  7. Validity: set to 9999 days (about 27 years) or 25 years. Don't set short — an expired keystore means you can't update APKs you signed with it.
  8. Name fields (First/Last Name, Org, etc): fill with anything — "Test", "RE", whatever. These appear in the certificate but don't affect functionality.
  9. Tap Create. The .jks file is generated at your chosen path.
  10. Back in Keystore Management — long-press your new keystore → Set as Default. A star or checkmark appears. This keystore is now used automatically for all signing operations.
// BACK IT UP NOWCopy your .jks file to Google Drive, cloud storage, or PC. Losing it means you can't update any APK you've already signed with it — you'd have to uninstall and reinstall every modded app from scratch every time you update.
Multiple Keystores — When and Why

You can create multiple keystores and switch between them. Reasons to use more than one:

  • Testing vs stable — one keystore for quick test installs you'll throw away, one for patches you'll keep long-term
  • App-specific — if an app checks its own installer signature or does cross-app verification, using a dedicated keystore per app keeps things clean
  • Sharing mods — if you share modded APKs, others need to install with your keystore's signature or uninstall their existing copy first

Switch default keystore: ≡ → Keystore Management → long-press another keystore → Set as Default.

What APK Tools Does

≡ → Functions → APK Tools gives you a sub-menu that wraps APKTool functionality directly inside MT Manager. It lets you fully disassemble an APK into a folder of readable files — and rebuild it back into an APK after editing.

This is different from the APK Editor (which edits inside the packed APK). APK Tools extracts everything to your filesystem first, you edit the extracted files, then rebuild.

Decompile APK → Folder

Functions → APK Tools → Decompile APK → select your APK → choose output folder.

MT Manager runs APKTool internally. Output folder contains:

output_folder/ ├── smali/ ← all classes as .smali files │ └── com/app/billing/ │ └── PurchaseManager.smali ├── smali_classes2/ ← classes2.dex disassembled ├── res/ ← decoded XML resources │ ├── layout/ ← readable XML layouts │ └── values/ ← strings.xml, colors.xml ├── AndroidManifest.xml ← decoded, readable └── apktool.yml ← rebuild config

When to use this over APK Editor:

  • When you want to edit resource XML files — layouts, strings, colors — these are fully decoded and editable as plain text
  • When making many Smali edits across multiple classes — editing .smali files directly in MT Manager's text editor is faster than navigating the DEX editor for each one
  • When you want to search across all Smali using MT Manager's file search — search for any string across the entire smali/ folder
  • When you need to add entirely new classes — drop a new .smali file into the right package folder
Build APK from Folder

After editing files in the decompiled folder: Functions → APK Tools → Build APK → select the output folder → MT Manager recompiles everything back into an unsigned APK.

  1. Build produces an unsigned APK. It is NOT signed yet.
  2. Long-press the built APK → Sign → your default keystore → signed copy created.
  3. Uninstall original if needed. Install your signed build.

Decompile Resources Only

Functions → APK Tools → Decompile Resources — only decodes resources.arsc and binary XML files. Does not disassemble DEX. Faster than full decompile.

Use this when you want to read or edit strings, layouts, or drawables without touching the code. Perfect for UI text changes, removing ads from layouts, or changing app icon.

Zipalign

Functions → APK Tools → Align APK — runs zipalign on your APK. Zipalign optimizes the APK so uncompressed files inside it are aligned to 4-byte boundaries. Android can then memory-map them directly instead of copying, reducing RAM use and load time.

Most of the time MT Manager aligns automatically during build. But if you manually edited files inside the ZIP (using Open As Archive → replace a file), the alignment may be broken. Always zipalign before signing when doing archive-level edits.

1. Edit → Build/Repack
2. Zipalign  ← must be BEFORE signing
3. Sign      ← must be AFTER zipalign

HEX EDITOR Low-Level File Editing
What the Hex Editor Is

The hex editor shows a file as raw bytes in hexadecimal. Every byte of the file is displayed as two hex characters. On the right side, bytes that correspond to printable ASCII characters appear as text — this is how you spot string literals embedded in binary files.

Long-press any file → Open With → Hex Editor. Or from inside the APK Editor, tap any file → Hex Editor option.

Reading the Hex Editor Layout
Offset   Hex bytes (16 per row)              ASCII
00000000  64 65 78 0A 30 33 35 00  D4 B4 C9 4C  dex.035.....L
00000010  00 00 00 00 00 00 00 00  00 00 00 00  ................
00000020  78 56 34 12 00 00 00 00  70 00 00 00  xV4.....p...
  • Left column — file offset in hex. 00000000 = byte 0, 00000010 = byte 16.
  • Middle columns — 16 bytes per row in hex. Each pair = one byte.
  • Right column — ASCII representation. Dots = non-printable bytes. Letters/numbers = readable text.
  • Selected byte — highlighted in both hex and ASCII columns simultaneously.
Hex Editor Controls
  • Search (magnifier icon) — search by: hex bytes (e.g. 12 00 0F 00), text string (searches ASCII/UTF-8), or UTF-16 string (for wide-character strings). Returns all occurrences with their offsets.
  • Edit mode (pencil icon, VIP) — tap to toggle edit mode. Tap any byte → keyboard appears → type new hex value. The byte changes live.
  • Go to offset — jump to a specific byte offset. Useful when you know the exact position of a value from prior analysis.
  • Undo/Redo — step through your edits.
  • Save — writes your changes to the file. For files inside an APK viewed via Open As Archive, changes are saved back into the archive.

Accessing DEX Search

TYPESEARCHESBEST FOR

Search Strategy — What to Type
  • String search first, always. Type the exact text from the paywall screen. Even 2–3 words of a dialog message. Results jump directly to the containing method.
  • Partial matches work. Searching "premium" finds "is_premium", "premium_user", "show_premium_dialog", "PremiumActivity". Cast wide, then narrow.
  • Case sensitivity. MT Manager's DEX string search is usually case-sensitive. Try both "Premium" and "premium" if first search returns nothing.
  • Log tags as class names. If logcat showed D/PurchaseManager, search Class type for "PurchaseManager". Even in obfuscated builds, the log tag string survives — search String type for "PurchaseManager" to find the class that logs it.
  • SharedPrefs keys. Search String for "is_premium", "sub_active", "subscription", "trial". These are developer-chosen names that are never obfuscated.
  • SDK class anchors. Search Class for "BillingClient", "Purchases" (RevenueCat), "Adapty". Non-obfuscated third-party class names that anchor you to the billing subsystem.

Every method in an app either calls other methods or is called by other methods. The call graph is the map of these relationships. When you RE a subscription gate, you're always tracing a path through this graph — from something visible (a string, a paywall screen) backwards to the boolean that controls access.

Tracing Backwards — Find Usage in JADX
  1. You found a method that shows the paywall — call it showPaywall(). You're in it in JADX.
  2. Right-click on the method name in the left panel (or on any call to it in the code) → Find Usage.
  3. Results panel shows every place showPaywall() is called from. Each result shows the calling class and method, with a code preview.

P2Google Play Billing State

App caches purchase state from Google Play Billing. onPurchasesUpdated() fires when a purchase completes or is restored — it saves the state somewhere. A separate getter reads it back.

// The listener — fires on purchase/restore:
public void onPurchasesUpdated(BillingResult result, List<Purchase> purchases) {
    if (result.getResponseCode() == BillingResponseCode.OK && purchases != null) {
        for (Purchase p : purchases) {
            if (p.getPurchaseState() == Purchase.PurchaseState.PURCHASED) {
                savePremiumState(true);  // ← this writes to prefs/db
            }
        }
    }
}

// The getter — reads cached state:
public boolean hasPurchase() {
    return this.isPurchased;  // field set by onPurchasesUpdated
}

// Patch options:
// 1. Patch hasPurchase() to return true always
// 2. Patch onPurchasesUpdated() to call savePremiumState(true) always
// 3. Patch savePremiumState() to always write true regardless of param

How to find it: JADX text search → Code → PurchasesUpdatedListener. The implementing class is the purchase manager. Every boolean method in it is a patch candidate.

P3RevenueCat / Adapty Entitlements

Third-party subscription SDKs wrap billing in their own entitlement system. The app calls the SDK, the SDK returns a CustomerInfo or Profile object, and the app checks a named entitlement on it.

// RevenueCat pattern (JADX view):

    public void onReceived(CustomerInfo customerInfo) {
        // entitlement key is the string to search for:

            unlockFeature();
        }
    }
    public void onError(PurchasesError error) { }
});

// Adapty pattern:

    public void onResult(AdaptyProfile profile) {
        if (profile.getAccessLevels().get("premium").isActive()) {
            unlockFeature();
        }
    }
});

How to find it: JADX text search → Code → CustomerInfo or AdaptyProfile or getEntitlements. The callback method is where you patch — make isActive() always return true, or skip the check and call unlockFeature() directly.

// Patch: hook isActive() with Frida (easier than APK patch here):

});
P4Server-Side Validation

App sends a request to its own server. Server checks subscription status against its database. Returns JSON. App reads the response and gates access on it.

// What the response handler looks like (JADX):
void handleLicenseResponse(JSONObject response) {
    try {
        boolean valid = response.getBoolean("is_valid");
        int expiry = response.getInt("expiry_ts");

How to find it: intercept traffic (see method G below), find the endpoint URL, search that URL string in JADX, find the class that calls it, find the response parser next to it.

AManifest — Map the Attack Surface

Before touching any DEX, read the manifest. It declares every launchable component and their permissions. In MT Manager: open APK as archive → tap AndroidManifest.xml. Or in JADX: left panel → AndroidManifest.xml node at the top.

What to look for:

  • Permissions declared — com.android.vending.BILLING confirms Google Play IAP. INTERNET with no billing permission = server-side check likely.
  • android:debuggable="true" — if present, ADB debugging already allowed. If absent, you can add it via a manifest patch to enable debugging.

5Encrypted Strings — Hook the Decryptor

DexGuard and Allatori encrypt string literals at compile time. At runtime, a decrypt helper decrypts each string on demand. You can't search for them statically — but you can intercept every decryption at runtime.

Identify the decryptor — it looks like this in JADX:

// Instead of string literals you see:
prefs.getBoolean(a.a(1337), false);
// a.a(int) is the decrypt method, 1337 is the encrypted key

// The decryptor class usually has:
// - a static byte[] or int[] array (the encrypted data)
// - a single static method a(int) returning String
// - simple XOR or AES decryption logic

Hook it with Frida to dump all strings:

Java.perform(function() {
    var Decryptor = Java.use("a.a");
    Decryptor.a.overload("int").implementation = function(id) {
        var result = this.a(id);
        console.log("[str] id=" + id + " → " + result);
        return result;
    };
});

Run the app through its full startup and billing flow. Every decrypted string prints with its ID. Now you have a complete map: a.a(1337) → "is_premium". Every call to a.a() in JADX is now readable.

Static approach (if you prefer no Frida): read the decryptor method in JADX, identify the algorithm (usually XOR with a hardcoded key or AES-ECB), reimplement it in Python, and decrypt the entire static array at once to get all strings upfront.

6Automated Deobfuscation Tools

These tools apply heuristic renaming automatically — useful as a first pass before manual analysis.

  • jadx --deobf — built into JADX. Renames short identifiers using context: jadx --deobf --deobf-min-len 3 app.apk -d ./out. The --deobf-min-len 3 flag only renames identifiers shorter than 3 characters — leaves longer names alone. Good starting point.
  • deobfuscator.io — web-based. Upload APK, it applies heuristic renaming based on how Android SDK classes are used. Returns a renamed APK you open in JADX. No account needed.
  • Simplify (github: CalebFenton/simplify) — runs the obfuscated DEX in a virtual environment, traces execution, and simplifies the output. Breaks string encryption by actually running the decrypt functions. Best for apps with custom string obfuscation.
  • apkid (pip install apkid) — fingerprints the APK to identify which tools built it and which obfuscator was used. Run it first to know what you're dealing with before choosing your deobfuscation strategy: apkid app.apk.

TECHNIQUES Patching Patterns
01Always Return True

The most common patch. Gut the method body, hardcode true.

# Before:
.method public isPremium()Z
    .registers 3
    iget-object v0, p0, Lcom/app/a;->b:Landroid/content/SharedPreferences;
    const-string v1, "premium_state"
    invoke-interface {v0, v1}, Landroid/content/SharedPreferences;->getBoolean(Ljava/lang/String;Z)Z
    move-result v0
    return v0
.end method

# After:
.method public isPremium()Z
    .registers 2
    const/4 v0, 0x1
    return v0
.end method
// REGISTERSAfter gutting, update .registers to match what you actually use. Only v0 + p0 = set to 2. Wrong count = VerifyError crash.
02Flip a Single Constant

Method is already a hardcoded return — just flip the value. Least invasive patch possible.

# Find and change 0x0 to 0x1:
const/4 v0, 0x0    # false
return v0
# ↓
const/4 v0, 0x1    # true
return v0

Don't touch .registers — register count stays the same. Single character edit.

03Flip or Skip a Branch

Method branches to paywall on false. Flip the condition so it branches on true instead — or bypass the check entirely with goto.

# Original — goes to :paywall if isPremium() is false:
invoke-virtual {p0}, Lcom/app/a;->a()Z
move-result v0
if-eqz v0, :paywall   # if false → paywall
# premium code...
:paywall
invoke-virtual {p0}, Lcom/app/b;->show()V
return-void

# Option 1 — flip the condition:
if-nez v0, :paywall   # now only goes to paywall if TRUE

# Option 2 — skip check entirely:
invoke-virtual {p0}, Lcom/app/a;->a()Z
move-result v0
goto :premium         # always jump to premium code
if-eqz v0, :paywall   # now unreachable
:premium
# premium code continues...
04Early Return — Kill a Void Method

Disable an ad loader, analytics call, or license checker that returns void. Insert return-void as the very first line.

.method public loadAd()V
    .registers 1

    return-void    # ← add this as first line
    # everything below is now dead code
.end method

Set .registers 1 (just p0). Don't touch .method or .end method lines.

05NOP Sled — Neutralize Specific Lines

Replace specific instructions with nop to kill them without changing surrounding control flow. Good for disabling individual calls mid-method without touching the structure.

# Kill a license check call without removing the method:
# Original:
invoke-virtual {p0}, Lcom/app/License;->checkLicense()V

# NOP'd (3 nops = 1 invoke-virtual instruction):
nop
nop
nop
// EASIER IN MT MANAGERJust delete the invoke line in the editor and save. MT Manager will error if there's a register/stack problem. Easier than manually counting nop widths.
06Patch a String Constant

Change hardcoded strings — API endpoints, license server URLs, validation keys.

# Original — points to real license server:
const-string v0, "https://api.paywall.com/v1/check"

# Patched — points to localhost (always fails gracefully):
const-string v0, "https://127.0.0.1/check"

In MT Manager: use Functions → Search in the DEX to find URL strings in hex, then edit. Or find via DEX string search and edit in the Smali editor.
