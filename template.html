CONCEPT What RE Actually Is
What Reverse Engineering Actually Means

When a developer builds an app, they write it in a programming language — Java or Kotlin for Android. A compiler then transforms that into a format your phone can run. When you download an app from the Play Store, you never see that original code. You get the compiled output only.

Reverse engineering is reading that compiled output, figuring out what the code does, and changing it. You don't need the original — everything the app needs to run is inside the APK, which means everything you need to understand and modify it is there too. That's the whole premise.

Why Android Apps Can Be Reversed

Android apps don't compile directly to raw machine instructions the way a C program does. Instead they compile to a middle format called DEX bytecode — think of it like a very detailed blueprint rather than the finished product. This blueprint is designed to run on Android's virtual machine, and because it's a blueprint rather than raw silicon instructions, it keeps a lot of the original structure intact — things like class names, method names, and how everything is organised.

A tool like JADX can take that blueprint and reconstruct something very close to the original Java code. Even when developers deliberately scramble the names (a technique called obfuscation), the actual logic — the thing that decides whether you're a premium user or not — is always still there. You just have to find it.

// COMPARE TO NATIVENative code compiled to ARM or x86 assembly loses almost all semantic information. Class names, method names, types — gone. Reversing a .so file requires Ghidra or IDA and weeks of manual analysis. DEX bytecode gives you back most of that for free. That's why apps that need serious protection move their DRM to native .so files.

javac / kotlinc — Source to .class

The Java or Kotlin compiler transforms source files into .class files — standard JVM bytecode. One .class file per class. At this stage the code targets the Java Virtual Machine, not Android specifically.

These .class files still don't run on Android — they need one more step.

d8 — .class to DEX

d8 (previously dx) is Google's DEX compiler. It takes all the .class files and merges them into one or more classes.dex files — Dalvik bytecode that Android can actually run.

Key things d8 does during this conversion:

  • Merges all classes from all .class files into a single DEX class pool
  • Converts JVM stack-based instructions to Dalvik's register-based instructions
  • Deduplicates string constants across the entire app into a shared string pool
  • Applies R8 (built-in optimizer + ProGuard replacement) if enabled — this is where obfuscation happens
  • Splits into multiple DEX files if the method count exceeds 65,536 (the multidex limit)
Multidex — Why There Are Multiple DEX Files

DEX files use a 16-bit index for method references. That caps you at 65,536 unique method references per DEX file. Large apps hit this limit easily — one app + all its third-party libraries can have 200,000+ methods.

Solution: split into multiple DEX files. classes.dex is the primary. classes2.dex, classes3.dex etc. are overflow files. Android loads all of them at startup.

// FOR PATCHINGThe class you need to patch might be in classes2.dex or classes3.dex, not the primary. In MT Manager's APK editor, you can tap into any DEX file separately. JADX loads all DEX files automatically when you open the APK.
baksmali / smali — DEX to Smali and Back

baksmali is a disassembler — it converts DEX bytecode into Smali, a human-readable text representation of the Dalvik instructions. MT Manager runs baksmali internally when you open a DEX file in the Smali editor.

smali is the assembler — it does the reverse, converting Smali text back to DEX bytecode. MT Manager runs smali internally when you save your edits.

You never run these tools manually. MT Manager handles both sides. But understanding that this conversion is happening explains why saving a method immediately validates your bytecode — the smali assembler is running and catching errors.

JADX — DEX Back to Java

JADX goes further than baksmali — instead of producing Smali assembly, it decompiles DEX back to Java pseudocode. It reconstructs if/else, for loops, try/catch, class hierarchies, generics.

The output is not real source code — it's a reconstruction, and it's not always perfect. Complex control flow, lambda expressions, and heavy obfuscation can confuse it. But even imperfect Java pseudocode is dramatically faster to read than raw Smali.

The workflow: use JADX to understand the logic and find where to patch, then use MT Manager to make the actual edit in Smali. JADX is your map. MT Manager is your scalpel.

RUNTIME Dalvik vs ART
What Actually Runs Your Code

Android has had two runtimes. Understanding both helps you understand what's happening when an app runs — and why certain patches work the way they do.

Dalvik — The Original (Android 1.0 – 4.4)

Dalvik was Android's original virtual machine. It interprets DEX bytecode at runtime using JIT (Just-In-Time) compilation — translating frequently-run bytecode to native machine code on the fly, caching the result.

Key characteristic: register-based VM. Unlike the JVM which is stack-based, Dalvik explicitly names registers (v0, v1, p0…) in every instruction. This is why Smali looks so different from JVM bytecode — it directly reflects Dalvik's register architecture. Dalvik is gone in modern Android, but the bytecode format it defined (DEX) is still what all Android apps compile to today.

ART — Android Runtime (Android 5.0+, current)

ART replaced Dalvik in Android 5.0 Lollipop. The key difference: ART uses AOT (Ahead-Of-Time) compilation. When you install an app, ART compiles the DEX bytecode to native machine code right then. The native code is stored in /data/dalvik-cache/ as an OAT file.

Modern ART uses a hybrid approach: some AOT compilation at install, JIT compilation for code paths discovered at runtime, and profile-guided optimization that improves over time as the app is used.

// WHY THIS MATTERS FOR REART still ships with and runs from DEX files — the OAT cache is just an optimization. When you patch the DEX in an APK and reinstall, ART recompiles your patched DEX fresh. The patch runs. The OAT cache is rebuilt from your modified DEX automatically.
FORMAT The APK — What It Really Is
An APK Is Just a ZIP

An APK (Android Package) is a standard ZIP file with a .apk extension. Every piece of data the app needs to run is inside it. Rename any APK to .zip on your PC and it opens in any archive tool.

In MT Manager: long-press any APK → Open As Archive — you're browsing the ZIP. You can extract individual files, edit them, and re-add them. That's all "modding" is at the file level.

Binary XML — AndroidManifest.xml

The AndroidManifest.xml inside an APK is NOT standard text XML. It's been compiled to a compact binary format called AXML (Android Binary XML) by aapt2 during the build. Opening it in a text editor shows garbage.

MT Manager automatically detects and decodes binary XML when you tap it in the APK editor — you see human-readable XML. When you save it, MT Manager re-encodes to binary. This is why you can edit the manifest in MT Manager but not in a plain text editor on the raw APK.

The same binary format applies to all XML files in res/. APKTool also handles this decoding/re-encoding, which is why it's the preferred tool for resource-heavy mods.

DEX How DEX Bytecode Works
What's Inside a DEX File

A DEX file isn't just a jumble of machine code — it has a very organised structure that actually makes our job easier. Here's what's in there:

SECTIONCONTENTS
HeaderMagic bytes (dex\n035\0), checksum, SHA-1 hash, file size, section offsets. The magic bytes confirm it's a valid DEX file.
String poolEvery string literal in the entire app — class names, method names, field names, string constants — deduplicated into one indexed list. This is why string searching is so fast and so powerful for RE.
Type poolAll type descriptors (class names in Smali format) referenced in the file. References into the string pool.
Proto poolMethod prototypes — parameter type lists and return types. Every unique method signature appears here once.
Field poolAll field definitions across all classes — name, type, declaring class.
Method poolAll method definitions — name, prototype, declaring class. Referenced by bytecode instructions.
Class defsClass definitions — superclass, interfaces, access flags, list of fields and methods with their code.
Code itemsThe actual bytecode for each method — register count, try/catch blocks, instruction stream.
// THE STRING POOL IS YOUR FRIENDBecause every string in the entire app is deduplicated into one searchable pool, when you search for a string in MT Manager's DEX editor or JADX, you're searching one indexed list. That's why string search is fast and reliable even in large apps — and why it's almost always your first move.
Why Smali Looks the Way It Does

When you open a method in MT Manager you'll see things like v0, v1, p0 everywhere. These are registers — named storage slots, like labelled boxes. Every instruction in Smali explicitly says "read from this box, write the result to that box." That's it.

Compare this to the JVM (what normal Java targets): instead of named boxes, it uses a stack — you push values on, pop them off. You can't see what's in the stack at any point; you just have to follow the pushes and pops mentally.

Dalvik's register approach is more code to write but much easier to read. const/4 v0, 0x1 means "put the number 1 into box v0." return v0 means "return whatever is in box v0." That's the whole method. No hidden stack state to track.

SMALI The Language You Edit
Smali — The Language You'll Actually Edit

Smali is a human-readable text version of DEX bytecode. Think of it like this: DEX is the binary file the phone actually runs, and Smali is a way of writing it that humans can read and edit. Every single Smali instruction translates directly to exactly one instruction in the binary. No magic in between.

When you open a method in MT Manager and tap Edit, you're editing Smali. When you hit Save, MT Manager converts your Smali back to DEX bytecode automatically. You never touch the binary directly. This is the layer where all your patches happen.

Smali vs Java — The Same Thing, Different View
// Java (what the dev wrote):
public boolean isPremium() {
    return true;
}

// Smali (what you edit in MT Manager):
.method public isPremium()Z
    .registers 2
    const/4 v0, 0x1
    return v0
.end method

Same logic. One is source, one is bytecode assembly. The Smali version has explicit register allocation (.registers 2), explicit type encoding (Z for boolean), and explicit register use (v0 holds the value). Everything implicit in Java is explicit in Smali.

Why Not Just Edit the Java in JADX?

JADX's Java output is a reconstruction — not real source code. It's JADX's best guess at what the original Java looked like, and it's often slightly off. You can't take JADX's output, make a change, and compile it back. It won't work.

Smali is the real thing. It maps directly to what's in the DEX file. When you edit Smali in MT Manager and hit Save, the DEX is updated immediately — no compilation, no guessing. That's why the workflow is: use JADX to read and understand the code, then go to MT Manager to edit the Smali. One tool for reading, one tool for writing.

// THE WORKFLOWRead logic in JADX (Java view). Understand what to change. Find the same method in MT Manager (Smali view). Make the change in Smali. The two tools complement each other perfectly.
ADB Android Debug Bridge
ADB — Your Phone's Remote Control

ADB (Android Debug Bridge) is a free tool that lets you talk to your Android phone from your computer via a USB cable or Wi-Fi. You type commands on your PC, and things happen on your phone.

For reverse engineering you'll use it to: pull APKs off the device, read crash logs when an app breaks, run commands as root, and connect tools like Frida. You don't strictly need it just for basic MT Manager patching — but the moment something breaks or you want to go deeper, ADB becomes essential.

Setup — Enable USB Debugging
  1. Enable Developer Options. Settings → About Phone → tap Build Number seven times. "You are now a developer" toast appears.
  2. Enable USB Debugging. Settings → Developer Options → toggle USB Debugging ON.

  4. Connect via USB. Plug in your phone. Run adb devices in terminal. Your phone shows a dialog: "Allow USB Debugging from this computer?" — tap Always Allow then Allow.
  5. Verify. Run adb devices again. You should see your device listed as device (not unauthorized).

ANALYSIS Static vs Dynamic
Two Ways to Approach Any App

Static analysis means reading the app's code without running it — like reading the recipe before you cook. You open the APK in JADX, read the decompiled Java, find what you want to change, patch it in MT Manager. No root needed, works on any device, and you can do it on your PC while your phone sits on the desk. This is your default approach.

Dynamic analysis means watching the app while it actually runs — like watching the chef cook and writing down what they do. You use Frida to hook methods in real time, intercept calls, and observe what actually happens when you tap that "Subscribe" button. Requires root. More powerful when static analysis hits a wall.

In practice: you'll almost always start static and switch to dynamic only when the app fights back.

PROTECTIONS What You'll Face
The Protection Landscape

Apps use layered protections. Knowing what each one is tells you what tool to reach for and roughly how hard the job is.

Level 1 — No Protection (Start Here)

Plenty of apps — especially smaller indie apps — ship with no protection at all. You open them in JADX and see exactly what the developer wrote: class called PurchaseManager, method called isPremium(). It's almost insultingly easy. Find the method, change it to return true, sign the APK, done. This is the best place to learn — start with unprotected apps and build muscle memory before moving to harder targets.

Level 2 — Names Are Scrambled (ProGuard/R8)

This is the default for almost every production app. The tool that builds the APK renames everything to single letters — PurchaseManager becomes a, isPremium() becomes a(). Looks intimidating. Isn't, once you know the trick.

Here's the key: only the names are scrambled. The logic — the actual code that decides if you're premium — is completely intact. You just need to find it without being able to search for "isPremium". The fix: search for strings like "is_premium" or "Subscribe" (those are never scrambled), then follow the code backwards to the gate.

Level 3 — The Strings Are Encrypted Too

Some obfuscation tools go a step further and encrypt every string in the app. Instead of "is_premium" sitting in the code, you see a.a(1337) — a call to a decryption function with a number. Your string search finds nothing because the string doesn't exist as readable text anywhere in the file.

The fix is simpler than it sounds: let the app decrypt its own strings. Hook that decryption function with Frida while the app runs. Every time the app decrypts anything, your hook logs it. Run the app for a minute and you've got a full dump of every string the obfuscator tried to hide. Then you know with a Python script.

Level 4 — The App Checks If You've Touched It

Some apps read their own signature at runtime — the cryptographic fingerprint that changes when you modify and resign the APK. If the signature doesn't match what the app expects, it knows it's been tampered with and either crashes or disables features.

It's like a tamper seal on medicine. When you resign with your own keystore, the seal is different. The app notices.

// What the check looks like in JADX:
PackageInfo info = pm.getPackageInfo(pkg, GET_SIGNATURES);
String sig = Base64.encode(info.signatures[0].toByteArray());
if (!sig.equals(EXPECTED_SIG)) { kill(); }

Broken by: find this check (search for getSignatures, GET_SIGNATURES, signatures[0]) and patch it to always pass. Or hook getPackageInfo() with Frida to return a fake signature matching the expected value.

Level 5 — The App Won't Run on Rooted Phones

Some apps — especially banking and DRM-heavy apps — refuse to run if they detect your phone is rooted. They check for things like: does the su binary exist? Is Magisk installed? Does the build look like a modified ROM?

Three ways around it: use Magisk's hide feature (Shamiko) to make your root invisible to specific apps. Or use Objection's one-liner android root disable which hooks all the detection methods. Or find the detection method in JADX and patch it to always say "nope, not rooted."

Level 6 — The App Only Trusts Its Own Server Certificate

Most apps send sensitive data over HTTPS, which is encrypted. Normally you could intercept that traffic with a proxy tool — but some apps go further and "pin" the certificate. That means the app has a hardcoded fingerprint of the exact certificate its server uses, and refuses to connect if it sees anything else — including your proxy's certificate.

You need this bypassed when you want to see what the app is sending to its license server. One command with Objection fixes it: android sslpinning disable. It hooks every known SSL library simultaneously.

Level 7 — The Real Logic Is in a .so File (Hard)

For serious DRM, developers move the subscription check out of Java entirely and into a native library — a .so file compiled from C or C++. Your phone runs this directly as machine code. There are no class names, no method names, no types. Just raw ARM instructions.

This is significantly harder to reverse. The standard approach is Frida — hook the bridge between the Java code and the native library (called JNI), intercept the result before it comes back to Java, and return "yes" regardless of what the native code computed. You don't need to understand the native code at all — just intercept the answer it gives.

Most subscription gates never go this deep. If you hit this, you've found a seriously well-protected app.

Level 8 — The Real Code Is Downloaded Later (Advanced)

The sneakiest approach: the APK you download from the Play Store is basically empty. On first run it downloads the real code from a server, decrypts it, and loads it on the fly. If you open the APK in JADX, you'll find almost nothing — just a loader shell.

The fix: use Frida to intercept the moment when that downloaded code gets loaded. Your hook runs before any of the loaded code executes, logs where the file is on disk, and you can pull it off the device. Then open it in JADX like you would any APK. The "trick" was the loading — the code itself is normal DEX once you have it.

WORKFLOW The Full Process — From Zero to Patched
  1. SETUP — Install MT Manager VIP. Create your signing keystore (≡ → Keystore Management → Create). Set it as default. Set up ADB if you'll be doing advanced work.
  2. EXTRACT — Get the target APK. MT Manager → Functions → Installed Apps → Extract APK. Copy to a working folder. Never work on the original.
  3. READ — Open the APK in JADX on PC. Browse the package structure. Find where billing logic lives. Note class names and method signatures. Understand the gating logic.
  4. ASSESS PROTECTIONS — Is it obfuscated? Does JADX show a.b.c or real names? Does it do network license checks? Does it check its own signature? This determines your approach.
  5. HUNT — Find the exact method to patch. Use string search, billing SDK anchors, logcat, Frida tracing — whichever fits the protection level. See the HUNT tab for all 9 methods.
  6. DECODE — If obfuscated, map the scrambled names to real purposes using type inference, JADX rename, log tags, and cross-references until you've identified the gate method.
  7. PATCH — Open the DEX in MT Manager. Navigate to the method. Tap Edit. Write your Smali patch (always-return-true, flip branch, early return, etc.). Update .registers. Save.
  8. SHIP — Save the APK in MT Manager (floppy disk). Sign it with your keystore. Uninstall original (different signature = required). Install your mod.
  9. TEST — Launch the app. Trigger the previously locked feature. Does it open? If yes — done. If the app crashes or the feature is still locked, go to step 10.
  10. DEBUG — Run adb logcat AndroidRuntime:E *:S. Read the crash. Find the method named in the stack trace. Fix the register count or restore what you broke. Repeat from step 7.

KEYSTORE Your Signing Identity
What's a Keystore and Why Do I Need One?

Think of a keystore as your personal stamp. Every APK needs to be stamped before Android will install it. The Play Store version of an app is stamped by the developer. When you modify the APK and repack it, you need to stamp it with your own stamp — that's your keystore.

Android tracks which stamp was used to install an app. If you try to install an app that was stamped by a different keystore than the one already installed, Android refuses — it thinks it's a different app trying to overwrite another. That's why you always have to uninstall the original before installing your mod. Once you've installed your mod, future patches stamped with your same keystore install as normal updates, no uninstall needed.

Create Your Keystore — Step by Step
  1. MT Manager → tap ≡ (top right hamburger) → Keystore Management.
  2. Tap + (or New) → Create Keystore.
  3. Keystore path: tap the folder icon → navigate to /sdcard/Mods/ → type filename my.jks → confirm. This is where the keystore file saves.
  4. Keystore password: any password you'll remember. Use the same as key password to keep it simple.
  5. Key alias: a label for this key entry. "mykey" or "patch" or anything. Not security-critical.
  6. Key password: same as keystore password is fine.
  7. Validity: set to 9999 days (about 27 years) or 25 years. Don't set short — an expired keystore means you can't update APKs you signed with it.
  8. Name fields (First/Last Name, Org, etc): fill with anything — "Test", "RE", whatever. These appear in the certificate but don't affect functionality.
  9. Tap Create. The .jks file is generated at your chosen path.
  10. Back in Keystore Management — long-press your new keystore → Set as Default. A star or checkmark appears. This keystore is now used automatically for all signing operations.
// BACK IT UP NOWCopy your .jks file to Google Drive, cloud storage, or PC. Losing it means you can't update any APK you've already signed with it — you'd have to uninstall and reinstall every modded app from scratch every time you update.
Multiple Keystores — When and Why

You can create multiple keystores and switch between them. Reasons to use more than one:

  • Testing vs stable — one keystore for quick test installs you'll throw away, one for patches you'll keep long-term
  • App-specific — if an app checks its own installer signature or does cross-app verification, using a dedicated keystore per app keeps things clean
  • Sharing mods — if you share modded APKs, others need to install with your keystore's signature or uninstall their existing copy first

APK TOOLS Decompile and Build
APK Tools — Unpack Everything at Once

The APK Editor mode (what you use for most patches) lets you navigate into the APK and edit things while it stays packed. APK Tools does the opposite — it completely unpacks everything into a normal folder of files on your phone, lets you edit them freely, then repacks it into an APK.

Think of it like the difference between editing a document inside a ZIP archive versus extracting the ZIP, editing the files normally, then re-zipping. Same result, different workflow. Use APK Tools when you want to make lots of changes to resource files (images, text, layouts) or when you want to search across all the Smali code at once using your file manager's search.

Functions → APK Tools → Align APK — runs zipalign on your APK. Zipalign optimizes the APK so uncompressed files inside it are aligned to 4-byte boundaries. Android can then memory-map them directly instead of copying, reducing RAM use and load time.

HEX EDITOR Low-Level File Editing
The Hex Editor — Reading Raw File Bytes

Every file on your computer is ultimately just a sequence of numbers (bytes). The hex editor shows you those numbers, two digits at a time, in hexadecimal (base-16, where digits go 0-9 then A-F). On the right side it also shows which bytes happen to look like readable text — this is how you spot things like URLs, keys, and strings buried inside binary files.

You probably won't use the hex editor often — the Smali editor handles most patches. But it's the right tool when you need to change a string inside a native .so file, patch a single byte, or verify that your Smali edit produced the bytes you expected.

Long-press any file → Open With → Hex Editor. Or from inside the APK Editor, tap any file → Hex Editor option.

CALL GRAPHS Following the Chain
Following the Trail Backwards

In any app, methods call other methods. When you tap "Subscribe", something calls something which calls something which eventually reads a boolean value and either unlocks the feature or shows the paywall. That chain of calls is what you're navigating.

The trick with finding gates is to start from something you can see — the paywall screen, a string from the dialog, a toast message — and work backwards through that chain until you find the boolean that started it all. Patch that boolean to always return true, and every step downstream behaves as if you're premium.

Tracing Backwards — Find Usage in JADX
  1. You found a method that shows the paywall — call it showPaywall(). You're in it in JADX.
  2. Right-click on the method name in the left panel (or on any call to it in the code) → Find Usage.
  3. Results panel shows every place showPaywall() is called from. Each result shows the calling class and method, with a code preview.

  5. That if condition is a method call. Right-click it → Go to declaration. You're now in the gate method.
  6. Verify: this method returns boolean. It reads some state (SharedPrefs, a field, a network response). When the state says "not premium" it returns false. This is your patch target.

Recognizing Gates on Sight

Most subscription gates follow one of a handful of patterns. Once you recognize the pattern, you know exactly what to patch without tracing the whole call graph. These are the five most common.

P2Google Play Billing State

App caches purchase state from Google Play Billing. onPurchasesUpdated() fires when a purchase completes or is restored — it saves the state somewhere. A separate getter reads it back.

// The listener — fires on purchase/restore:
public void onPurchasesUpdated(BillingResult result, List<Purchase> purchases) {
    if (result.getResponseCode() == BillingResponseCode.OK && purchases != null) {
        for (Purchase p : purchases) {
            if (p.getPurchaseState() == Purchase.PurchaseState.PURCHASED) {
                savePremiumState(true);  // ← this writes to prefs/db
            }
        }
    }
}

// The getter — reads cached state:
public boolean hasPurchase() {
    return this.isPurchased;  // field set by onPurchasesUpdated
}

// Patch options:
// 1. Patch hasPurchase() to return true always
// 2. Patch onPurchasesUpdated() to call savePremiumState(true) always
// 3. Patch savePremiumState() to always write true regardless of param

How to find it: JADX text search → Code → PurchasesUpdatedListener. The implementing class is the purchase manager. Every boolean method in it is a patch candidate.

P3RevenueCat / Adapty Entitlements

Third-party subscription SDKs wrap billing in their own entitlement system. The app calls the SDK, the SDK returns a CustomerInfo or Profile object, and the app checks a named entitlement on it.

// RevenueCat pattern (JADX view):

    public void onReceived(CustomerInfo customerInfo) {
        // entitlement key is the string to search for:
        if (customerInfo.getEntitlements().get("premium").isActive()) {
            unlockFeature();
        }
    }
    public void onError(PurchasesError error) { }
});

// Adapty pattern:

    public void onResult(AdaptyProfile profile) {
        if (profile.getAccessLevels().get("premium").isActive()) {
            unlockFeature();
        }
    }
});

How to find it: JADX text search → Code → CustomerInfo or AdaptyProfile or getEntitlements. The callback method is where you patch — make isActive() always return true, or skip the check and call unlockFeature() directly.

});
P4Server-Side Validation

App sends a request to its own server. Server checks subscription status against its database. Returns JSON. App reads the response and gates access on it.

// What the response handler looks like (JADX):
void handleLicenseResponse(JSONObject response) {
    try {
        boolean valid = response.getBoolean("is_valid");
        int expiry = response.getInt("expiry_ts");
        saveLicenseState(valid, expiry);
    } catch (JSONException e) {
        saveLicenseState(false, 0);  // ← patch this to true
    }
}

// 2. Intercept the network response with mitmproxy,
//    change is_valid to true at the proxy level
// 3. Patch the reader that calls handleLicenseResponse
//    to supply a fake {is_valid:true} JSON object

How to find it: intercept traffic (see method G below), find the endpoint URL, search that URL string in JADX, find the class that calls it, find the response parser next to it.

AManifest — Map the Attack Surface

Before touching any DEX, read the manifest. It declares every launchable component and their permissions. In MT Manager: open APK as archive → tap AndroidManifest.xml. Or in JADX: left panel → AndroidManifest.xml node at the top.

  • android:debuggable="true" — if present, ADB debugging already allowed. If absent, you can add it via a manifest patch to enable debugging.

F.1 — Hook a simple method (no overloads)

F.2 — Hook overloaded methods

Overloaded methods share a name but have different parameter types. Java allows this; Frida requires you to specify which overload you want.

// JADX shows two versions of checkAccess():
// boolean checkAccess()  ← no params
// boolean checkAccess(String userId)  ← takes String

Java.perform(function() {
    var Target = Java.use("com.app.Auth");

    // Hook the no-param version:
    Target.checkAccess.overload().implementation = function() {
        console.log("[+] checkAccess() → true");
        return true;
    };

    // Hook the String-param version:
    Target.checkAccess.overload("java.lang.String")
        .implementation = function(userId) {
        console.log("[+] checkAccess(" + userId + ") → true");
        return true;
    };

    // Hook ALL overloads at once (when you want to cover all versions):
    Target.checkAccess.overloads.forEach(function(ov) {
        ov.implementation = function() {
            // Call original and log what it returned:
            var ret = ov.apply(this, arguments);
            console.log("[checkAccess] args:",
                JSON.stringify([].slice.call(arguments)),
                "→ returned:", ret);
            return true; // override return
        };
    });
});

F.3 — Hook constructors ($init)

Constructors initialize objects. Some apps set subscription state during construction — a boolean field set in <init> based on a SharedPrefs read. Hook $init to intercept or modify that initialization.

// Hook a constructor — intercept object creation:
Java.perform(function() {
    var Session = Java.use("com.app.UserSession");

    // No-arg constructor:
    Session.$init.overload().implementation = function() {
        console.log("[+] UserSession() constructed");
        // Call original constructor first:
        this.$init();
        // Now modify the freshly created object:
        this.isPremium.value = true;   // set the boolean field directly
        console.log("[+] isPremium field forced to true");
    };

    // Constructor with params (String userId, Context ctx):
    Session.$init
        .overload("java.lang.String", "android.content.Context")
        .implementation = function(userId, ctx) {
        console.log("[+] UserSession(" + userId + ") constructed");
        this.$init(userId, ctx); // call original
        this.isPremium.value = true;
    };
});
// READING + WRITING FIELDSthis.fieldName.value reads or writes an instance field directly. this.fieldName.value = true sets a boolean field. This works on any field Frida can see — use it after calling the original constructor to patch object state right at birth.

F.4 — Hook methods with object parameters

When a method takes an object (not a primitive), you can read or modify that object's fields, call its methods, or replace it with a different object entirely.

// Method: void handlePurchase(Purchase purchase)

    var Manager = Java.use("com.app.billing.BillingManager");
    var Purchase = Java.use("com.android.billingclient.api.Purchase");

    Manager.handlePurchase
        .overload("com.android.billingclient.api.Purchase")
        .implementation = function(purchase) {

        // Read fields/methods of the passed object:
        console.log("Purchase state: " + purchase.getPurchaseState());
        console.log("SKU: " + purchase.getSkus());

        // Call original with the real object:
        this.handlePurchase(purchase);
    };

    // Or: intercept a response parser that reads JSON
    var JSONObject = Java.use("org.json.JSONObject");
    var Api = Java.use("com.app.network.LicenseApi");

    Api.parseResponse.overload("org.json.JSONObject")
        .implementation = function(json) {

        // Log what the server actually returned:
        console.log("Server response: " + json.toString());

5Encrypted Strings — Hook the Decryptor

DexGuard and Allatori encrypt string literals at compile time. At runtime, a decrypt helper decrypts each string on demand. You can't search for them statically — but you can intercept every decryption at runtime.

Identify the decryptor — it looks like this in JADX:

// Instead of string literals you see:
prefs.getBoolean(a.a(1337), false);
// a.a(int) is the decrypt method, 1337 is the encrypted key

// The decryptor class usually has:
// - a static byte[] or int[] array (the encrypted data)
// - a single static method a(int) returning String
// - simple XOR or AES decryption logic

Hook it with Frida to dump all strings:

Java.perform(function() {
    var Decryptor = Java.use("a.a");
    Decryptor.a.overload("int").implementation = function(id) {
        var result = this.a(id);
        console.log("[str] id=" + id + " → " + result);
        return result;
    };
});

Run the app through its full startup and billing flow. Every decrypted string prints with its ID. Now you have a complete map: a.a(1337) → "is_premium". Every call to a.a() in JADX is now readable.

Static approach (if you prefer no Frida): read the decryptor method in JADX, identify the algorithm (usually XOR with a hardcoded key or AES-ECB), reimplement it in Python, and decrypt the entire static array at once to get all strings upfront.

You're not breaking the obfuscation yourself — you're making the code break its own obfuscation for you. The output file is dramatically easier to read than what went in.

When to use it:

TECHNIQUES Patching Patterns
01Always Return True

The most common patch you'll ever make. You've found the method that checks if someone is premium — it reads from SharedPrefs, checks a field, whatever. You don't care about any of that anymore. Just delete everything inside the method and make it always return true.

# Before:
.method public isPremium()Z
    .registers 3
    iget-object v0, p0, Lcom/app/a;->b:Landroid/content/SharedPreferences;
    const-string v1, "premium_state"
    invoke-interface {v0, v1}, Landroid/content/SharedPreferences;->getBoolean(Ljava/lang/String;Z)Z
    move-result v0
    return v0
.end method

# After:
.method public isPremium()Z
    .registers 2
    const/4 v0, 0x1
    return v0
.end method
// REGISTERSAfter gutting, update .registers to match what you actually use. Only v0 + p0 = set to 2. Wrong count = VerifyError crash.
02Flip a Single Constant

Sometimes the developer already hardcoded the return value — maybe they left it as return false during testing. Lucky you: instead of rewriting the whole method, you change one character. 0 becomes 1. False becomes true.

# Find and change 0x0 to 0x1:
const/4 v0, 0x0    # false
return v0
# ↓
const/4 v0, 0x1    # true
return v0

Don't touch .registers — register count stays the same. Single character edit.

03Flip or Skip a Branch

Sometimes the method doesn't just return a boolean — it branches. "If the user is NOT premium, show the paywall." You can either flip the condition (change the "if not" to "if yes") so the paywall only shows for premium users, or skip the check entirely with a goto that jumps straight to the premium code.

# Original — goes to :paywall if isPremium() is false:
invoke-virtual {p0}, Lcom/app/a;->a()Z
move-result v0
if-eqz v0, :paywall   # if false → paywall
# premium code...
:paywall
invoke-virtual {p0}, Lcom/app/b;->show()V
return-void

# Option 1 — flip the condition:
if-nez v0, :paywall   # now only goes to paywall if TRUE

# Option 2 — skip check entirely:
invoke-virtual {p0}, Lcom/app/a;->a()Z
move-result v0
goto :premium         # always jump to premium code
if-eqz v0, :paywall   # now unreachable
:premium
# premium code continues...
04Early Return — Kill a Void Method

Want to kill a method completely? For void methods (ones that don't return a value) — like ad loaders, analytics calls, or license checkers — just add return-void as the very first line. The method will immediately exit before doing anything. Everything after it is dead code.

.method public loadAd()V
    .registers 1

    return-void    # ← add this as first line
    # everything below is now dead code
.end method

Set .registers 1 (just p0). Don't touch .method or .end method lines.

05NOP Sled — Neutralize Specific Lines

Replace specific instructions with nop to kill them without changing surrounding control flow. Good for disabling individual calls mid-method without touching the structure.

# Kill a license check call without removing the method:
# Original:
invoke-virtual {p0}, Lcom/app/License;->checkLicense()V

# NOP'd (3 nops = 1 invoke-virtual instruction):
nop
nop
nop
// EASIER IN MT MANAGERJust delete the invoke line in the editor and save. MT Manager will error if there's a register/stack problem. Easier than manually counting nop widths.
06Patch a String Constant

Change hardcoded strings — API endpoints, license server URLs, validation keys.

# Original — points to real license server:
const-string v0, "https://api.paywall.com/v1/check"

# Patched — points to localhost (always fails gracefully):
const-string v0, "https://127.0.0.1/check"

In MT Manager: use Functions → Search in the DEX to find URL strings in hex, then edit. Or find via DEX string search and edit in the Smali editor.

07Manifest Patches — No Code Needed

Edit AndroidManifest.xml directly in MT Manager APK Editor. MT Manager decodes binary XML automatically.

  • Add android:debuggable="true" to <application> — enables ADB debugging
  • Remove android:allowBackup="false" — enables ADB backups
  • Remove specific <uses-permission> entries to block access
  • Add android:networkSecurityConfig="@xml/nsc" + create res/xml/nsc.xml to allow HTTP traffic for traffic analysis
  • Remove android:testOnly="true" if present
08Frida Hook — No APK Modification

Patch at runtime without touching the APK. Requires root + Frida server running on device.

// Hook isPremium() to always return true:
Java.perform(function() {
    Java.use("com.app.License").isPremium
        .implementation = function() {
        console.log("[+] isPremium hooked → true");
        return true;
    };
});

EDIT Making the Edit in MT Manager
Making Your Edit in MT Manager — Step by Step
  1. Navigate to your target method (package → class → method). Tap it.
  2. Tap the pencil (Edit) icon — top right of the Smali viewer. Raw text editor opens.
  3. The keyboard toolbar above the keyboard has shortcuts: Tab, braces, semicolons. Use them — Smali syntax is unforgiving.
  4. Make your edit. Change 0x0 to 0x1, gut the body, flip a branch — whatever technique fits.
  5. Update .registers count if you removed or added local variables.
  6. Tap Save (checkmark). MT Manager validates the bytecode. Error = fix it. Clean = saved to in-memory DEX.
// VALIDATE BEFORE MOVING ONIf MT Manager shows an error on save, fix it before navigating away. The error message names the problem — wrong register count, bad opcode, missing return. Don't ignore it and force-save.

ERRORCAUSE + FIX

Zero to Patched Subscription — 13 Steps

Scenario: app has a premium feature locked. Tap it — paywall appears. Goal: make it always open.

  1. Extract APK. MT Manager → ≡ → Functions → Installed Apps → find app → Extract APK → copy to /sdcard/Mods/target.apk.
  2. Scan the manifest. Long-press → Open As Archive → tap AndroidManifest.xml. Note exported activities, billing receivers, declared services.
  3. Open APK Editor. Long-press → Open With → MT Manager.
  4. Search for paywall string. Tap classes.dex → Smali Editor → search icon → String type → search the text on the paywall button or dialog. MT Manager finds the containing class and method.
  5. Navigate to the result. Tap the search result. You're in the method that shows the paywall. Read it — look for what condition triggers this code.
  6. Find the gate method. Back out to the class. Look for a ()Z method — no params, returns boolean. That's the check that gate-keeps access.
  7. Read the gate. Tap it. Confirm it returns false for non-subscribers. Note the .registers count.
  8. Edit. Tap pencil icon. Delete everything between .registers N and .end method. Type: const/4 v0, 0x1 then new line: return v0.
  9. Fix registers. Change .registers N to .registers 2. Tap Save. No errors = good.
  10. Save APK. Back out to APK Editor root → tap floppy disk → wait for repack.
  11. Sign. Long-press the modified APK → Sign → your default keystore → done. Note the _signed.apk output path.
  12. Uninstall original. Settings → Apps → your target → Uninstall.
  13. Install mod. Long-press target_signed.apk → Install. Launch. Tap the previously locked feature — it opens.
